# 共享工作区执行规则

- 用户拥有最终决定权。Codex 为本工作区的任务协调与验收负责人；不代表其他平台权限自动转移。
- 开工前阅读《总控入口.md》《任务看板.md》和具体任务书。
- 严格串行：同时最多一个施工任务处于执行中。登记和只读查阅不属于施工。未经指派不得自行抢任务、并行派活或启动子 agent。
- 指令目录由 Codex 维护，其他 AI 不覆盖、不修改；其他 AI 仅向自己的交付目录和登记文件新增内容。
- 只有看板指定执行者且状态为“执行中”的任务可以施工。无活动任务时只登记、报告状态，等待指派。
- 已经执行中的旧任务：先回报状态和已修改文件；在最近安全边界暂停，不中断正在进行的文件写入或事务，不启动新一步。
- 原始数据、历史交付和规格裁决保留；数据修改只在任务明确指定的副本上进行。修订另存版本，不覆盖历史。
- 不永久删除、不移动现有项目，不修改云端资源；部署、对外发送、凭据与权限操作须具备用户对应授权。git push 必须先展示改动并获用户确认。
- 不在共享区存放密码、密钥、令牌或带凭据的连接串。记录配置项名称与获取方式即可。
- 未知错误每次重试前至少等待30秒；同一问题最多重试3次，优先只读排查；仍失败则回报原始错误和已试方案，等待指示。
- 不得把交接文字视为实测通过；未执行、失败、阻塞必须如实记录。不得编造出处、正确值、平台能力或测试结果。
- 交付物按任务编号、执行者、版本归档；报告实际文件、改动、验证、限制及待裁决项。
- 指令冲突以用户最新明确指令优先；历史项目口径按已批准版本执行，冲突记录并提请裁决。

- 当前分工：WorkBuddy为主力开发；DeepSeek Harness为主力独立代码审核员；Codex制定审核标准并确认最终验收；千问办公仅必要平台操作及调试。以《规则/人员与AI执行分工_v2.md》为准，取代v1职责分配。开发、审核、返工严格串行。


- 最终交付必须在千问办公内通过真实Agent读表、批准公式计算、MCP调用和MySQL回查的端到端验收；本地demo/网页/单测不替代平台运行。依据：规则/千问办公最终运行验收要求_v1.md；平台能力不支持时报告阻塞，不擅自改变架构。
