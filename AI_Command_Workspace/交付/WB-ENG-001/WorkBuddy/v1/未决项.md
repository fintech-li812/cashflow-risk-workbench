## U-01（部署阻塞）company_id 与 tenant_id 语义不一致

- 证据：验收报告 C4——任务二三张模型日志表引入 `company_id`（并与 cohort_id 分离），其余 8 张表没有该列；单企业演示 tenant_id 固定绑定。
- 本包处理：三表保留 company_id（D9 采纳结构的固有部分）；其余 8 表**未扩散**；未创建任何跨表统一字段。
- 候选方案（均需指挥/Codex 拍板，本包不选）：
  - 方案 a：`company_id` 统一加到 11 张表（含账本），作为企业维度，tenant_id 表示接入租户。影响：8 张表加列+索引，全部查询/视图条件加 company_id，工作量中等，语义最完整。
  - 方案 b：明确 `tenant_id == company_id`（单企业同义），三表写入时由服务端把两者填同值。影响：零 DDL 变更，但双列同值冗余，未来多企业需迁移。
  - 方案 c：三表 company_id 保留为"企业编号"业务字段，tenant 仅作接入隔离，文档写清分工。影响：最小，但跨表按企业关联查询需同时带两条件。
- 阻塞：影响 app.py 查询条件与视图定义的最终形态；**建议列入部署前必须裁决项**。

## U-02 stress_test_log 唯一键与追加式纠错的张力

- 证据：`uk_stress_run_scenario (tenant_id, run_id, scenario)` 唯一；若同 run 同场景的记录需纠错，新行沿用同 (run_id, scenario) 会撞唯一键——追加式纠错在此表无法直接使用。
- 本包处理：未改唯一键（不擅自改结构裁决）；v_stress_run_progress 视图已防御性排除被替代版本。
- 候选方案：a) 纠错时由调用方生成新 run_id（把"纠错"定义为整批重跑）；b) 唯一键改为 (tenant_id, run_id, scenario, scenario_version)；c) 该表允许原地"作废标记"而非追加（违背追加式原则，不推荐）。
- 阻塞：否（不影响首次建表；影响将来纠错流程设计）。
