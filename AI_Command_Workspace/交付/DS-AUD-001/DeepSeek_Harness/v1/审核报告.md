## 5. 必改缺陷（P2）

### R-01（P2）log_feedback 强制 actual_value，导致"pending 无实际值"状态无法合法提交

- 位置：`candidate\docs\千问办公_MySQL_MCP工具定义_v1.1.json:304-317`（required 含 `predicted_value`、`actual_value`），`:373-377`（actual_value 为 string + 金额 pattern）
- 对照证据：
  - `candidate\sql\init_v1.1.sql:155-156`：`predicted_value DECIMAL(20,2) NULL`、`actual_value DECIMAL(20,2) NULL`（DDL 允许空）
  - `candidate\sql\init_v1.1.sql:158`：`accuracy_label` 三值含 `pending`
  - 协议 `:157`："缺乏实际数据时不得生成'准确'标签"
- 触发：实际值尚未产生、需登记 `accuracy_label=pending` 的反馈。
- 预期：可省略 actual_value（或显式 null），由服务端写 NULL。
- 实际：探针 E3.4——省略 actual_value 被 Schema 拒绝（`'actual_value' is a required property`）；传 null 也被拒绝。
- 影响：唯一可行的"合法"提交是填 0 或假数，这会把"未到实际期"写成"已对照"，污染准确率分母；与"未运行值必须 NULL、不补 0、不伪造"的项目红线直接冲突。
- 修改方向（二选一，需作者与 Codex 确认口径）：① 从 required 移除两金额，类型改为 `["string","null"]`，服务端按 `accuracy_label` 校验（accurate/inaccurate 必须有 actual，pending 必须无 actual）；② 明确 pending 反馈必须走另一入口，并同步改协议与 DDL 语义。
- 复验条件：pending + 省略 actual_value 通过 Schema；accurate/inaccurate 缺 actual_value 由服务端拒绝（Schema 层允许可选）；真实 MySQL 插入 NULL 成功（需环境）。

### R-02（P2）audit_id 的契约类型不一致：JSON 为自由字符串，DDL 为 BIGINT

- 位置：`...工具定义_v1.1.json:402-407`（audit_id：string，maxLength 128，无 pattern）；`init_v1.1.sql:152`（`audit_id BIGINT UNSIGNED NULL COMMENT '关联 audit_log.id'`）；`:107`（`audit_log.id BIGINT UNSIGNED AUTO_INCREMENT`）
- 协议示例：`:242`、`:249` 返回 `"audit_id":"A-demo-001"`（非数字串）。
- 触发：调用方把 log_to_mysql 返回的 audit_id 原样回填 log_feedback（协议就是这样示范的）。
- 预期：ID 形态唯一，能直接入库。
- 实际：探针 E3.5——`"A-demo-001"` 被 Schema 判为合法；按 DDL 该值写入 BIGINT 列在严格模式下会失败（或需服务端静默改写，破坏"回显即为凭据"的可核对性）。
- 影响：反馈与审计的关联链在示例路径上走不通；两套 ID 语义（自增数字 vs 业务串）没有映射规则。
- 修改方向：统一为一种——若以 `audit_log.id` 为关联键，Schema 改为数字字符串（pattern `^[0-9]{1,20}$`）并把协议示例改成真实形态；若坚持业务串，则 DDL 改 VARCHAR 并说明与自增 id 的关系。两者都需同步协议 §5.3/§六示例。
- 复验条件：协议示例与 Schema/DDL 三者一致；非数字 audit_id 被拒；真实插入通过（需环境）。

### R-04（P2）v_template_published_latest 未排除被替代版本，同 effective_from 时返回多行

- 位置：`init_v1.1.sql:588-598`（视图定义）；`:188`（param_template.supersedes_id 存在）；`:593`（只过滤 `publication_status='published'`）
- 对照：其余 6 个纠错类视图都带 `NOT EXISTS (... supersedes_id ... AND s.tenant_id=...)`（`:522-586`、`:601-619`）；本视图没有。
- 触发：对已发布模板做追加式纠错（新行 `supersedes_id` 指向旧行，按 `uk_tpl_ver` 需换 template_version，effective_from 可能沿用或相同）。
- 预期：省略版本号读取时只返回当前有效的最新发布版本（1 行）。
- 实际：旧行仍为 published，仍参与 `MAX(effective_from)`；若旧行是最大值，视图返回旧行；若两行 effective_from 相同，返回 2 行。
- 影响：`load_param_template` 省略版本号时可能取到被替代参数或无法确定唯一行，直接污染 K 黄/K 红等计算输入（业务参数本身不受影响，受影响的是"取哪一版"）。
- 为什么作者测试没发现：`validate_contract.py:474-482` 的 C17 只检查"含 NOT EXISTS 的视图"是否有 tenant 限定，天然覆盖不到一个没有 NOT EXISTS 的视图。
- 修改方向：加 `AND NOT EXISTS (SELECT 1 FROM param_template s WHERE s.supersedes_id=p.id AND s.tenant_id=p.tenant_id)`；对 effective_from 并列给出确定规则（如 `ORDER BY p.id DESC LIMIT 1` 或新增 active 标记），并在 CHECK/唯一键层面表达"同企业同行业仅一个 active 发布"（若可表达）。加一条静态/集成校验防止回归。
- 复验条件：构造"旧行被替代 + 同 effective_from"两例，视图仅返回新行且仅 1 行；脚本新增对应断言。
